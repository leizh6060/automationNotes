# Infrastructure Tribal Knowledge Interview Checklist

**Purpose:** Extract undocumented operational knowledge from the people who currently run the systems, before automating them.

## How to use this

- Run one session per system/service owner, 45–60 minutes each. Don't try to cover everything in one marathon interview.
- Record the session (with permission) — people describe gotchas casually and won't repeat the same detail twice.
- Bring the current-state inventory you already have (from automated discovery) so you're not wasting time asking things you can look up. Use the interview for the _why_, not the _what_.
- End every section with: "What haven't I asked about that I should know?"

---

## 1. Warm-up / scope

- [ ] What system(s) or services are you the primary owner or go-to person for?
- [ ] How long have you been responsible for this, and who had it before you?
- [ ] Is there anyone else who knows this system as well or better than you?

## 2. Deployment & change process

- [ ] Walk me through the last time you deployed a change to this system, step by step.
- [ ] Which of those steps are manual vs. scripted/automated?
- [ ] Is there a specific order dependencies must be deployed/restarted in?
- [ ] Are there times of day/week you avoid making changes? Why?
- [ ] Has a deployment ever gone wrong here? What happened and what did you learn?
- [ ] Is there a rollback process? Has it actually been tested/used?

## 3. Configuration & secrets

- [ ] Where do configuration values live today (files, env vars, a wiki, someone's head)?
- [ ] Are there config values that differ between environments in ways that aren't obvious?
- [ ] Where are secrets/credentials stored, and who has access?
- [ ] Are there hardcoded values anywhere that should really be parameters?
- [ ] Any config that "just works" but nobody's sure why it's set that way?

## 4. Dependencies & blast radius

- [ ] What does this system depend on to function?
- [ ] What depends on this system that might not be obvious from the architecture diagram?
- [ ] If this system went down right now, what would break, and who would notice first?
- [ ] Are there any shared resources (databases, file shares, queues) with informal or undocumented sharing rules?
- [ ] Any external/third-party dependencies with quirks (rate limits, flaky APIs, manual renewal steps)?

## 5. Known issues & workarounds

- [ ] What's the thing about this system that always breaks, and how do you fix it when it does?
- [ ] Are there manual workarounds currently in place for known bugs?
- [ ] Is there anything you have to "remember to do" that isn't written down anywhere?
- [ ] Are there alerts you've learned to ignore? Why?
- [ ] What's the scariest part of this system to touch, and why?

## 6. Monitoring & incident response

- [ ] How do you know when something's wrong with this system?
- [ ] Walk me through the last incident — how was it detected, diagnosed, and resolved?
- [ ] Are there manual health checks you do that aren't captured by monitoring?
- [ ] Who gets paged, and does that match who can actually fix the problem?

## 7. History & rationale

- [ ] Why was this built/configured this way? (Especially anything that looks unusual.)
- [ ] Has this system survived a migration, rewrite, or major incident that shaped how it's built today?
- [ ] Is there anything here that's a temporary fix that became permanent?
- [ ] Are there naming conventions, tags, or patterns that mean something specific to this team?

## 8. Compliance, access & constraints

- [ ] Are there approval or change-management steps required before touching this system?
- [ ] Any data residency, retention, or regulatory constraints tied to this system?
- [ ] Who currently has access, and is that access list accurate/up to date?
- [ ] Are there audit or compliance requirements that automation needs to preserve (e.g., logging every change)?

## 9. Wrap-up

- [ ] If you left tomorrow, what's the one thing you'd want written down before you go?
- [ ] What haven't I asked about that I should know?
- [ ] Who else should I talk to?

---

## After the interview

- Write up notes within 24 hours — details fade fast, especially the offhand "oh yeah, also..." comments.
- Tag each item as: **Automate**, **Needs fixing before automating**, or **Just document** (some tribal knowledge is a process fix, not an automation target).
- Cross-check answers against your automated discovery data — contradictions are often the most valuable finding, since they reveal outdated assumptions or undocumented drift.
