A practical framework:

1. Define automation targets first
    

- Candidate workflows: provisioning, patching, scaling, backups, remediation, drift detection, compliance checks.
    
- For each: trigger, inputs, expected output, rollback path, blast radius, owner, SLO.
    

2. Inventory and identity
    

- Servers, VMs, containers, clusters, network devices, databases, queues, storage, DNS, load balancers.
    
- Identifiers: hostname/instance ID, IP, environment, region/zone, app/service, owner, team, lifecycle status, criticality.
    
- Sources: cloud APIs, Kubernetes API, Ansible/Terraform/Pulumi state, CMDB, config management like Chef/Puppet/Salt, network discovery.
    

3. Configuration and desired state
    

- IaC definitions: Terraform/OpenTofu, Pulumi, CloudFormation, Bicep, Helm charts, Kustomize.
    
- Runtime config: Ansible playbooks, systemd units, kernel/OS settings, firewall rules, IAM policies.
    
- Detect drift between “declared” state and actual state.
    

4. Dependencies and data flow
    

- Service dependency map: which components call which, ports/protocols, timeouts, auth requirements.
    
- Data classification: PII, secrets handling, encryption requirements, retention, residency.
    
- Use APM/tracing, service mesh, load balancer rules, flow logs, and docs/runbooks.
    

5. Observability and operational signals
    

- Metrics/logs/traces; alerts and alert history; incident tickets; postmortems.
    
- “Runbook actions” are often the best first automations: repeated manual steps with clear success criteria.
    

6. Access, security, and compliance
    

- AuthN/AuthZ model, secrets locations, RBAC boundaries, jump hosts, cert management.
    
- Required controls: audit logs, approvals, change windows, segregation of duties.
    
- Never automate with broad long-lived credentials; prefer OIDC/workload identity and short-lived tokens.
    

7. Change and incident history
    

- Deployment history, rollback history, failed changes, common failure modes.
    
- Source systems: Git history, CI/CD logs, ticketing (Jira/ServiceNow), chatops channels.
    

8. Normalize into a machine-usable model Recommended schema per resource:
    

- id, type, environment, owner, region/zone, dependencies, desired_state_ref, current_state_ref, sensitivity, automation_allowed, rollback_ref, last_verified_at.
    
- Store in a CMDB or graph DB if complex; keep GitOps repo as source of truth where possible.
    

9. Validate before automation
    

- Dry-run/detect mode first; then notify-only; then enforce with guardrails.
    
- Use canary environments, policy-as-code checks, approval gates for high-risk changes.
    

Minimum viable collection for day 1:

- Environment inventory from cloud/K8s/CMDB
    
- Critical apps and owners
    
- Existing IaC and runbooks
    
- Top 5 repeated manual tickets
    
- Monitoring/alerts for those workflows
    
- Secrets/access model at a high level
    

Rule of thumb: automate what is observable, reversible, and owned. Avoid automating opaque or unowned systems until the data is trustworthy.


# tep-by-Step: Collecting Information for Nutanix Infrastructure Automation

## Phase 1 — Access & Environment Discovery

1. **Identify Prism Central (PC) instances** — PC is your main automation/API endpoint. List all PC IPs/FQDNs and versions.
    
2. **Map Prism Element (PE) clusters** — For each PC, list registered clusters (cluster name, AOS version, cluster UUID, IP/CVM info).
    
3. **Inventory blocks/nodes** — Model, BIOS/firmware versions, node serials, IPMI details, disk layout per CVM.
    
4. **Record foundation data** — If clusters were deployed via Foundation, export cluster config and node images.
    
5. **Verify API access** — Test Prism Central v3 REST API and decide credentials strategy (local account vs. AD/LDAP mapped role).
    

## Phase 2 — API & Tooling Setup

6. **Choose your automation tools**:
    
    - **Terraform** — `nutanix/nutanix` provider
        
    - **Ansible** — `nutanix.ncp` collection
        
    - **PowerShell** — `Nutanix.PowerShell` module
        
    - **Python/Go** — direct v3 API calls
        
    - **nCLI** — Nutanix CLI (runs on CVM, useful for discovery)
        
7. **Create service account** — Dedicated automation user in PC with least-privilege role (e.g., Cluster Admin for read, restricted for writes).
    
8. **Test read-only queries** — Pull clusters, VMs, subnets, images, categories via API to validate access.
    

## Phase 3 — Resource Inventory (via Prism Central v3 API)

9. **VMs** — UUID, name, state, cluster placement, vCPU/RAM, disks, NICs, categories, protection status.
    
10. **Images** — UUID, name, type (disk/ISO), source URI, cluster availability.
    
11. **Subnets & networking** — VLANs, IPAM pools, VPCs (flow networking), external subnets, floating IPs.
    
12. **Storage** — Storage containers, capacity/usage, dedup/compression settings, default container policies.
    
13. **Categories** — Key/value pairs used for policy, placement, and automation (e.g., `Environment:Prod`, `Team:DBA`).
    
14. **Projects** (if using Calm/Self-Service) — Quotas, assigned users, networks, defaults.
    

## Phase 4 — Cluster & System Configuration

15. **AOS/AHV settings** — Cluster name, NTP/DNS, timezone, RF factor, compression/dedup, RF tolerance.
    
16. **Network config per cluster** — Bond modes, bridge/ uplink configs, AHV networks, MTU, flow enablement.
    
17. **Data protection** — Protection domains, replication targets (remote PC/sites), snapshot schedules, retention policies.
    
18. **Licensing** — License type/quantity, expiry — automation breaks if licenses lapse.
    
19. **VM templates/golden images** — Capture how base images are built and updated (this is your provisioning baseline).
    

## Phase 5 — Operational Data

20. **Alerts & events** — Export PC alert history to find recurring issues (disk failures, capacity warnings, HA events).
    
21. **Capacity & performance metrics** — Use v2/v3 metrics APIs or Prism capacity planning: CPU/RAM/storage headroom per cluster.
    
22. **Task history** — Long-running/repeated manual tasks in Prism (VM clones, image updates) = automation candidates.
    
23. **Runbooks & SOPs** — Any existing Nutanix operations docs (cluster expand, firmware update, DR failover).
    

## Phase 6 — Security & Governance

24. **RBAC mapping** — Roles in PC, AD/LDAP groups, what each team can do.
    
25. **Authentication** — Directory services, SSO config, certificate setup.
    
26. **Flow microsegmentation** — Security policies and app tiers (critical if automating VM provisioning).
    
27. **Audit trail** — PC audit logs for change tracking.
    

## Phase 7 — Consolidate & Prioritize

28. **Normalize data** — One inventory file/DB: `name, uuid, type, cluster, environment, category, owner, automation_eligible`.
    
29. **Tag with categories** — Apply missing categories — they're the backbone of Nutanix policy automation.
    
30. **Score automation candidates** — Frequency × toil × risk. Typical first wins:
    

- VM provisioning from golden images
    
    - Snapshot/backup scheduling
        
    - Category/policy enforcement
        
    - Reporting across clusters

```plain
# nCLI (on a CVM) — read-only discovery
ncli cluster info
ncli vm list
ncli storagepool list
ncli network list
ncli protection-domain list

# Prism Central v3 API examples
GET https://<PC>:9440/api/nutanix/v3/vms/list
GET https://<PC>:9440/api/nutanix/v3/subnets/list
GET https://<PC>:9440/api/nutanix/v3/images/list
GET https://<PC>:9440/api/nutanix/v3/clusters/list
```

**Key tip:** Everything in Nutanix automation flows through **Prism Central + v3 API + Categories** — get those three right and inventory collection is mostly scripted.

## Matrix B: Automation Candidate Scoring (prioritize what to automate)

|Workflow|Frequency (1–5)|Manual Effort hrs/mo|Risk Level (1–5)|Data Readiness|Reversibility|**Score**|
|:--|:-:|:-:|:-:|:-:|:-:|:-:|

|   |   |   |   |   |   |   |
|---|---|---|---|---|---|---|
|Example: VM provisioning from template|5|40|2|High|Easy (delete VM)|**High**|
|Example: Firewall rule changes|3|10|5|Medium|Hard|**Low first**|

**Scoring formula:** `Score = (Frequency × Effort × Data Readiness) ÷ (Risk + 1)`

|Score|Decision|
|:--|:--|

|   |   |
|---|---|
|> 30|Automate now (read-only/detect mode first)|
|15–30|Automate after guardrails/approvals|
|< 15|Document only, revisit later|
