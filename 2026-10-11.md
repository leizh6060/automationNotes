**IaC captures your entire environment in text files** that describe your infrastructure declaratively or imperatively. These files specify:

- **Networks:** Virtual networks, subnets, security groups, routing rules.
- **Compute resources:** Virtual machines, containers, serverless functions.
- **Storage:** Databases, blob storage, file shares.
- **Other services:** Load balancers, CDNs, monitoring tools.

You check these definition files into **version control** (like Git), treating them just like application source code. This enables:

- **Change tracking:** See who changed what and when.
- **Code review:** Team members review infrastructure changes before deployment.
- **Rollback capability:** Return to previous versions if problems arise.
- **Branch strategies:** Test infrastructure changes in separate branches.

For example, adding a new server becomes simple:

1. Edit the infrastructure definition file.
2. Submit a pull request for review.
3. Merge and run the deployment pipeline.
4. The new server provisions automatically.

No need to remote into environments or follow multi-step manual procedures.

- **Observability and Monitoring**: Implement monitoring, logging, and observability practices to track system health, performance metrics, and deployment status. 1. The On-Prem Information Gathering Checklist

Hypervisor & Compute (The Virtual Layer)

Before writing code, map out exactly how your virtual machines (VMs) are allocated:

- **Hypervisor API Access:** Ensure you have administrator credentials and API access enabled for your hypervisor (e.g., vCenter credentials for VMware or API tokens for Proxmox).
- **Resource Pools:** Document available CPU, RAM, and local or Network Attached Storage (NAS/SAN) datastores.
- **VM Inventory:** Document existing VM specifications (vCPUs, allocated RAM, disk sizes, and MAC addresses).
- **OS Images:** Locate the paths to your base ISO files or VM templates (e.g., Ubuntu Cloud-Init images, Windows Server templates).

Networking & Bare Metal (The Physical Layer)

Unlike the cloud, where networking is purely software-defined, on-prem IaC must safely overlay onto your physical network:

- **VLAN Maps:** Document all VLAN IDs and how they map to your VM port groups.
- **IP Address Management (IPAM):** Identify your subnet masks, gateways, and the pool of static IPs available for automation. _Crucial:_ Ensure your IaC tool does not accidentally deploy a VM onto an already-occupied static IP.
- **DNS & DHCP Servers:** Note your local primary/secondary DNS servers and Active Directory controllers (if applicable).
- 2. How to Automate Data Collection On-Prem

Since cloud discovery tools like `Former2` won't work inside your private data center, use these local strategies to collect data:

- **Export via Hypervisor CLI/PowerShell:** Run scripts against your hypervisor to dump the current inventory.

    - _For Proxmox (pvesh):_ `pvesh get /cluster/resources --type vm`
    
- **Nmap Subnet Scans:** Run a fast terminal command to find all active hosts on your management subnet to double-check against your documentation: `nmap -sn 192.168.1.0/24`

Before writing provisioning code, you must extract parameters to configure your IaC provider.

Document where the VirtIO ISO is stored in your Nutanix Image Service so your automation code can mount it during deployment.

2. Commvault Backup Mapping

To prevent your automated infrastructure from being unprotected, your code must enroll new workloads into your backup schedules immediately.

- **CommCell / Command Center API:** Collect the API endpoint of your Commvault environment.
- **Server Plan Names:** Identify the specific Commvault "Server Plans" (SLA policies, retention periods, and storage pools) intended for production vs. development.
- **Access Nodes (Proxies):** Note the capacity and placement of your Commvault Virtual Server Agent (VSA) / Access Nodes running in Nutanix to ensure backup data flows efficiently.

3. Guest OS Specifications (80/20 Split)

Because you have a mixed OS environment, you must catalog two distinct workflows:

- **For Windows (80%):** Document Active Directory domain join credentials, Windows License keys (KMS/MAK), and WinRM (Windows Remote Management) security certificates for post-deployment configuration.
- **For Linux (20%):** Collect Cloud-Init configuration configurations, SSH public keys, and internal package repository mappings.

2. The Integrated End-to-End Automation Workflow

Instead of running individual scripts, your collected data feeds a continuous delivery pipeline. Here is how your technologies communicate sequentially during a server build:

```
[ ServiceNow ] ──(Trigger API)──> [ Terraform / Ansible ]
                                         │
       ┌─────────────────────────────────┼────────────────────────────────┐
       ▼                                 ▼                                ▼
[ Cisco Network ]                 [ Nutanix AHV ]                 [ Active Directory ]
Allocates IP/VLAN                 Provisions VM Hardware          Creates Computer Object
       │                                 │                                │
       └─────────────────────────────────┼────────────────────────────────┘
                                         ▼
                                  [ Windows / Linux ]
                                  Configures Guest OS
                                         │
       ┌─────────────────────────────────┴────────────────────────────────┐
       ▼                                                                  ▼
 [ System Center (SCCM) ]                                          [ Commvault Backup ]
 Installs Apps & Patches                                           Enrolls in SLA Policy
```

1. **The Request (ServiceNow):** A user requests a Windows Server via the ServiceNow Service Catalog. ServiceNow generates an IP address and calls the IaC engine.
2. **Provisioning (Terraform):** **[Terraform's Nutanix Provider](https://registry.terraform.io/providers/nutanix/nutanix/latest/docs)** talks to Prism Central to create the VM using the designated Cisco VLAN and hooks up the correct Nutanix storage container.
3. **Identity & Domain (Ansible / Cloud-Init):** As the VM boots, **Ansible** connects via WinRM to join the Windows machine to **Active Directory** under the correct target OU.
4. **Software & Security (SCCM & Commvault):**
    - Ansible triggers the installation of the **SCCM Client**. SCCM takes over to install corporate baseline apps and security updates.
    - Simultaneously, the **Commvault Ansible Collection** registers the new server into the Commvault Command Center, attaching it to a predefined Server Plan.
5. **Close Loop (ServiceNow):** The pipeline updates the **ServiceNow CMDB** to mark the asset as "Active" and closes the request ticket.
